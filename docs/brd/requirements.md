## AUTH

Section: 6.1 Authentication, sessions and device pairing (AUTH)

- **AUTH-001** (M) Staff log in on shared devices by selecting their name/photo tile, then entering a numeric PIN (4 digits by default; the owner may require 6 ⚙ ). Choosing a name first means PINs need not be unique, and setting a PIN can never reveal someone else's.
- **AUTH-002** (M) PINs shall never be stored, transmitted in logs or displayed in plain text. They shall be hashed with bcrypt (cost ≥ 12) or Argon2id (blueprint). Before hashing, they are combined with a server-side secret ("pepper") kept outside the database and protected by Windows DPAPI. A 4-digit PIN has only 10,000 combinations, so without the pepper a stolen database could be brute-forced in seconds.
- **AUTH-003** (M) After 5 failed attempts within 10 minutes (blueprint) a staff login is locked for 15 minutes ⚙ or until a manager unlocks it. Attempts are also rate-limited per device.
- **AUTH-004** (M) One reusable PIN-pad component is used for login and manager overrides across the POS, KDS, waiter app and table tablet (blueprint).
- **AUTH-005** (M) On successful login the server issues a short-lived signed access token (≤ 15 min ⚙ ) bound to staff member, role, restaurant and device, plus a refresh mechanism (blueprint: JWT). Sessions expire after inactivity (POS and waiter devices: 10 min ⚙ ) and are renewed automatically while the person is actively using the app (blueprint). KDS screens run in device-authenticated station mode: actions are attributed to the station. Individual kitchen logins can be switched on ⚙.
- **AUTH-006** (M) The Owner account uses a strong password (≥ 12 characters) plus a TOTP second factor, which works offline. Both are required for: archive and purge, backup restore, full data export, license/subscription screens, tax and invoice settings, and creating or removing managers.
- **AUTH-007** (M) Device pairing. Every device (KDS screen, waiter phone, table tablet, pager, manager's browser) must be paired by a manager before it can talk to the server. 1. The manager generates a one-time pairing QR code (valid 10 min ⚙ ). 2. The device presents it. 3. The server issues a per-device credential (key pair or client certificate), stored in the device's secure storage (Android Keystore, ESP32 encrypted storage, browser non- exportable key). Requests from unpaired devices are rejected even when a valid PIN is entered.
- **AUTH-008** (M) Unpairing a device, or deactivating a staff member, revokes their tokens and closes their live connections within 5 seconds.
- **AUTH-009** (M) Each table tablet is paired to one table; re-assigning it requires a manager PIN. A tablet can only read or act on its own table.
- **AUTH-010** (M) Role-based access control per §4.2 is enforced on the server for every REST call, socket event and MQTT topic. Hiding buttons in the UI is not a security control.
- **AUTH-011** (M) Manager override: actions marked PIN in §4.2 prompt for a manager's PIN on the current device. The audit log records both the requester and the approver.
- **AUTH-012** (S) The Owner can create custom roles by combining permissions.
- **AUTH-013** (M) Logins, logouts, failed attempts, lockouts and overrides are written to the audit log (AUD).
- **AUTH-014** (M) Vendor staff have no standing access to a restaurant's local system (see UPD-008, UPD-009).

## ONB

Section: 6.2 Installation and onboarding (ONB)

- **ONB-001** (M) A single signed Windows installer sets up: the Local Server and PostgreSQL as auto-starting Windows services; the watchdog; the POS/Manager desktop app. No manual database setup is needed (blueprint).
- **ONB-002** (M) Data drive selection. The installer lists local fixed drives with free space and defaults to the first non-system drive (e.g., D:) if one exists. Otherwise it uses C: and shows a warning. It refuses network and removable drives and requires ≥ 20 GB ⚙ free space.
- **ONB-003** (M) Activation requires a one-time activation code issued from the Vendor Control Plane. It binds the license to the restaurant and the PC (LIC-004).
- **ONB-004** (M) The first-run setup wizard is usable by a non-technical manager, saves progress and can be resumed. Steps: 1. Restaurant profile: legal name, display name, address, state, GSTIN, FSSAI license number, logo, contact, business hours, business-day cut-off time (default 04:00 ⚙ ). 2. Tax setup: tax groups (e.g., "GST 5 %" = CGST 2.5 % + SGST 2.5 %; rates entered by the restaurant, never hard-coded), SAC code, prices tax-inclusive or tax-exclusive ⚙, rounding rule. 3. Invoice settings: series prefix, financial-year reset, header/footer, service charge (off by default). 4. Accounts: Owner (password + 2FA), managers. 5. Floor: sections and tables (number/name, capacity). Visual drag-and-drop layout is S. 6. Stations and printers: kitchen stations; network printer auto-discovery (S) or manual IP (blueprint); test print; station ↔ printer mapping; per-station mode screen / print / both (blueprint). 7. Menu import (ONB-005, ONB-006). 8. Staff and PINs, section assignment. 9. Device pairing: tablets, waiter phones, KDS screens, pagers. 10. QR codes: generate and print table tents (PDF, A6/A5). 11. Go-live check: a guided test order through every path (waiter, tablet, QR, KDS, pager, bill) before going live.
- **ONB-005** (M) Excel/CSV menu import using a vendor-provided template: categories, items, prices, tax group, veg/non-veg/egg, tags, station, description, synonyms. Variants, modifiers and combos go in companion sheets. A validation report lists every error before anything is committed.
- **ONB-006** (S) AI-assisted menu import. Upload photos or a PDF of the printed menu. A Vendor Control Plane service extracts it into the template structure. A mandatory human review screen shows every item before commit. Requires internet; the AI provider's API key is held only in the vendor cloud.
- **ONB-007** (S) Bulk photo upload, matched automatically to items by file name or item code, with manual correction.
- **ONB-008** (M) Onboarding can be done on-site or remotely. Remote onboarding uses a screen-sharing session started by the restaurant (UPD-009).
- **ONB-009** (M) Target: a restaurant with ≤ 150 items and ≤ 40 tables is fully operational within one business day, with the menu imported in ≤ 1 hour.
- **ONB-010** (S) Export and import of settings, for moving to a new PC or reinstalling.
- **ONB-011** (M) A printable site-readiness checklist covering PC spec, UPS, staff Wi-Fi separated from guest Wi-Fi, 2.4 GHz coverage in kitchen and floor, printer network, tablet offline speech pack (TAB-007) and BitLocker (SEC-007).

## MENU

Section: 6.3 Menu management (MENU)

- **MENU-001** (M) Structure: Menu → Categories (ordered, one level of sub-categories) → Items.
- **MENU-002** (M) Item attributes: name, short code, description, photo, base price, tax group; food type (veg / non-veg / egg), spice level (0-3), tags (Jain, bestseller, chef's special, allergens, custom); kitchen station, estimated prep time; availability, optional stock count, display order; visibility per channel (POS, waiter app, tablet, QR); external ID (INT-005).
- **MENU-003** (M) Variants (e.g., Half/Full, Regular/Large), each with its own price.
- **MENU-004** (M) Modifier groups (e.g., "Roti type", "Spice level", "Add-ons") with required/optional, minimum/maximum selections and price deltas (+/−). A group can be reused across many items (blueprint).
- **MENU-005** (M) Combos: a bundle of existing items and/or choice slots (e.g., "any 1 beverage") at a fixed price, with an optional active date range and time window for festivals or seasonal promotions (blueprint). Kitchen tickets always show each component item separately (blueprint).
- **MENU-006** (M) Availability and stock (blueprint): Authorised roles (§4.2) can mark an item out of stock, or set a remaining quantity. The quantity decreases with each approved order and the item switches to out of stock at 0. Changes reach every in-restaurant device within 2 s, and the QR menu within 30 s when online. Items become non-orderable immediately.
- **MENU-007** (S) Time-based availability (e.g., breakfast items 07:00-11:00 ⚙ ).
- **MENU-008** (M) Photos are stored locally, auto-resized into standard renditions (WebP) and served to in-restaurant devices. They are mirrored to cloud storage for the QR menu (blueprint). Uploads up to 5 MB, compressed automatically; metadata (EXIF) stripped.
- **MENU-009** (M) Price changes apply only to new order lines; open orders keep the price at the time of ordering. Every price change is audited.
- **MENU-010** (M) Items that have ever been ordered cannot be deleted, only archived (hidden), to preserve reports.
- **MENU-011** (M) Each item can have search synonyms (e.g., "panir", "cottage cheese"), used by text and voice search.
- **MENU-012** (M) Every ordering surface (POS, waiter app, tablet, QR menu) uses the same menu data and the same variant/modifier/combo selection logic and UI behaviour, built from shared components (blueprint).
- **MENU-013** (M) Menus are versioned. Tablets and waiter apps cache the current menu locally and refresh when a change event arrives, or on reconnection.

## TBL

Section: 6.4 Tables, sections and sessions (TBL)

- **TBL-001** (M) Sections (e.g., Ground floor, Terrace) contain tables. A table has a number/name, capacity, section, QR code and, optionally, a paired tablet.
- **TBL-002** (M) Waiter assignment: at shift start the manager assigns waiters to sections, and optionally to individual tables. The responsible waiter for a table is its assigned waiter; this can be overridden per table session.
- **TBL-003** (M) Table session: a waiter (app) or cashier/manager (POS) opens a table, which records seated-at time, number of guests (covers) and responsible waiter, and unlocks the table tablet. The session ends when the bill is settled and the table closed; the tablet then resets (TAB-003).
- **TBL-004** (M) Table states: Free → Occupied → Bill requested → Bill printed → Settled/Free. "Needs cleaning" is S.
- **TBL-005** (M) Move table (blueprint): moves an open session and all its orders from one table to a free table. Kitchen tickets update in place with a note such as "Moved from T4 to T7". No duplicate tickets. The old table's tablet resets; the new table's tablet unlocks.
- **TBL-006** (S) Merge tables into one bill; transfer individual items between tables.
- **TBL-007** (M) Table overview on the POS and manager dashboard, updated live without refresh (blueprint). For each table it shows: state, time seated, amount spent so far, responsible waiter; pending approvals and active service requests. Tapping a table opens its current order and running total (blueprint). From there the cashier can print the bill and close the table.
- **TBL-008** (M) Takeaway orders are created at the POS (waiter app is S) with a token number and optional customer name/phone. No table is involved.

## ORD

Section: 6.5 Order management, all channels (ORD)

- **ORD-001** (M) Order sources: POS, waiter app, table tablet, QR menu. Each order records its source, device and creating user (for staff) or table (for customers).
- **ORD-002** (M) Orders and order items follow the state machine in Appendix B.
- **ORD-003** (M) Customer-originated orders (tablet and QR) require approval by a waiter, or by a cashier/manager, before reaching the kitchen. The approver can change quantities or remove items (with the diner's agreement) before approving, or reject with a reason. The diner's screen shows the status throughout.
- **ORD-004** (M) Approval can be given from: the waiter app; the POS; the table tablet itself, by the waiter entering their PIN ("Approve at table"), so approval happens while talking to the diner.
- **ORD-005** (M) A pending approval alerts the responsible waiter (pager + app) and escalates to the manager if not acknowledged within N seconds ⚙ (NTF-005).
- **ORD-006** (M) Staff-originated orders (POS, waiter app) go to the kitchen directly when "Send KOT" is pressed.
- **ORD-007** (M) When an order is approved or sent: items are split by kitchen station, and one KOT is produced per station (screen, print or both per station setting); combos are exploded into their components; variants, modifiers and instructions appear under each item.
- **ORD-008** (M) KOT numbers are sequential per business day. Each KOT shows table/token, waiter, source, time, KOT number and order number.
- **ORD-009** (M) A table session can contain multiple orders and KOTs (rounds). The bill aggregates all of them.
- **ORD-010** (M) Item status (Pending approval → Sent → Preparing → Ready → Picked up → Served, or Rejected / Cancelled / Voided) is broadcast in real time to the POS, manager dashboard, waiter app, KDS and the table's tablet (blueprint).
- **ORD-011** (M) Cancellation rules. Before submission, the diner or waiter can freely edit the cart. After submission but before approval, the approver can edit or reject. After Sent but before Preparing, a waiter can cancel with a reason. The KDS shows the cancellation prominently, and a "CANCELLED" slip prints if the station prints. After Preparing, only a void is possible, needing a manager PIN and a reason. It appears in the voids/wastage report.
- **ORD-012** (M) Changes after a KOT (quantity, instruction) generate a "MODIFIED" delta ticket. Nothing changes silently.
- **ORD-013** (M) Idempotency (blueprint). Every submission carries a client-generated unique ID. Retries, double taps and relay replays never create duplicate orders, KOTs or stock deductions.
- **ORD-014** (M) The server recomputes all prices, taxes, discounts and availability from its own data. Prices sent by any client are ignored.
- **ORD-015** (M) Special instructions per item (≤ 140 characters ⚙ ) and per order.
- **ORD-016** (S) Hold and fire: a waiter can hold items (e.g., mains) and release them to the kitchen later.
- **ORD-017** (M) If an item becomes unavailable between adding it to the cart and submission, the server rejects that line with a clear message. The user can confirm submission of the rest.

## KDS

Section: 6.6 Kitchen Display System and kitchen printing (KDS)

- **KDS-001** (M) The KDS is a browser-based mode of the web console, served by the local server. It runs full-screen on any modern browser device (Android tablet/TV, mini-PC) that has been paired as a KDS device.
- **KDS-002** (M) Each KDS device is assigned one or more stations and shows only their tickets. An "Expo/Pass" view of all stations is S.
- **KDS-003** (M) A ticket card shows: KOT number, table/token, waiter, source, live time since sent; items with quantity, variant, modifiers and instructions, with combo components grouped under the combo name; badges for Moved, Modified and Cancelled.
- **KDS-004** (M) Ticket age uses colour thresholds ⚙ (default green < 10 min, amber 10-20 min, red > 20 min), always paired with an icon or text, not colour alone.
- **KDS-005** (M) Per-item and per-ticket actions: Mark preparing and Mark ready (blueprint). "Ready" triggers the notification to the responsible waiter (NTF). Bump removes a completed ticket; Recall restores recently bumped tickets.
- **KDS-006** (M) Ready-not-collected (blueprint): if ready items are not picked up within X minutes ⚙ (default 3), the ticket flashes and shows a "Notify manager" button that sends an alert to the manager on duty. Automatic escalation without pressing the button is S ⚙.
- **KDS-007** (M) Items are marked picked up at the pass on the KDS, or by the waiter in the app.
- **KDS-008** (M) Printing (blueprint): Each station's mode is screen, print or both ⚙. Printers can be network (IP) or USB, ESC/POS, 80 mm or 58 mm. KOTs can be reprinted. If a printer is offline, the POS and manager are alerted. In print-only mode KOTs are queued and printed on recovery, or reprinted on another printer chosen by the manager.
- **KDS-009** (M) Audible chime for new tickets; a distinct sound for cancellations and modifications; volume ⚙.
- **KDS-010** (S) All-day summary: total quantity of each item pending across open tickets.
- **KDS-011** (M) Dark theme by default, readable from 2 m, touch targets ≥ 48 px, usable with wet or gloved hands.
- **KDS-012** (M) On connection loss the KDS shows a full-screen "Disconnected" banner, reconnects automatically and resynchronises without losing or duplicating tickets.
- **KDS-013** (C) Bump-bar hardware support.

## BILL

Section: 6.7 POS billing, payments and day-end (BILL)

- **BILL-001** (M) A bill for a table session or takeaway order shows: itemised lines (variants, modifiers, combos), quantity, unit price, line total; subtotal, discounts, service charge (if enabled); taxes per tax group with the CGST/SGST split; round-off and grand total; amount in words is S.
- **BILL-002** (M) Bills carry GST invoice particulars, with templates configurable to the restaurant CA's guidance: legal name, address, GSTIN, FSSAI license number; invoice number and date/time, SAC code, place of supply (state), tax breakdown; customer name and GSTIN, when given (B2B).
- **BILL-003** (M) Invoice numbering. Unique and consecutive within each financial year, ≤ 16 characters, with a configurable prefix. Numbers are never reused or skipped. Cancelled invoices stay in the series with status Cancelled.
- **BILL-004** (M) Tax rates are configured per tax group and never hard-coded. Prices can be tax-inclusive or tax-exclusive ⚙.
- **BILL-005** (M) Discounts: item-level or bill-level, percentage or flat, with a mandatory reason. Each role has a limit ⚙ (e.g., cashier ≤ 10 %); above the limit needs a manager PIN. Complimentary (100 %) items need a manager PIN.
- **BILL-006** (M) Service charge is disabled by default. If enabled, it is labelled voluntary on the bill and can be removed at the diner's request (audited), consistent with consumer- protection guidelines (§12).
- **BILL-007** (M) Split bill by items or into equal parts. Each part gets its own invoice number.
- **BILL-008** (M) Payment recording (no integration): Modes: Cash, Card, UPI, Other ⚙, with split across modes allowed. Cash tendered and change due are recorded; a reference number for card/UPI is optional. A bill is settled when recorded payments equal the total.
- **BILL-009** (M) Reprints are marked "DUPLICATE" and audited.
- **BILL-010** (M) Editing a printed bill (items, discount) needs a manager PIN and a reason, and the audit log stores before/after values. A settled bill cannot be edited: it can only be voided and re-issued, which needs a manager PIN. The voided invoice keeps its number and the new invoice gets a new number.
- **BILL-011** (M) Customer details are optional: name, phone (with an explicit consent checkbox for digital bill/feedback), GSTIN.
- **BILL-012** (S) Digital bill by WhatsApp or SMS through a vendor-configured provider, sent only with consent and queued while offline. Bill content leaves the restaurant only for this purpose, and any hosted copy expires ⚙ (default 30 days).
- **BILL-013** (M) Shift and day-end. Open a shift with an opening cash float; record cash in/out with a reason. Close the shift with expected vs. counted cash (denomination count is S); the variance is recorded. Day-end produces the Z-report and closes the business date. Open tables block day- end unless a manager carries them forward with a PIN.
- **BILL-014** (M) Bill printing on an ESC/POS printer (80 mm/58 mm) with a configurable template (logo, header, footer) and on-screen preview.
- **BILL-015** (M) A bill request from the tablet or waiter notifies the cashier (POS) and the responsible waiter, and sets the table state to Bill requested.
- **BILL-016** (S) Cash-drawer kick through the receipt printer. "No-sale" drawer openings are audited.
- **BILL-017** (C) Dynamic UPI QR with the amount on the bill; card-terminal and payment- gateway integration.

## WTR

Section: 6.8 Waiter (Captain) app (WTR)

- **WTR-001** (M) An Android app delivered as a signed APK, installed and updated through MDM or an in-app updater (UPD-001). It runs only on paired devices, with PIN login.
- **WTR-002** (M) Home: "My tables" (assigned section) showing table state, seated time, pending-approval badge and active service requests. A toggle shows all tables.
- **WTR-003** (M) Order taking: open a table (covers, waiter); browse categories, text search, item details; variant/modifier popup (shared component, MENU-012), combos, quantity, special instructions; Send KOT.
- **WTR-004** (M) Approvals inbox: tablet and QR orders for the waiter's tables. The waiter can view, edit, approve, or reject with a reason.
- **WTR-005** (M) Service-request inbox: Water / Waiter / Bill requests with table and age. Actions: acknowledge, resolve (clears the request, same as Cancel on the tablet). Alerts use a banner, sound and vibration that are hard to miss even when the app is in the background or the screen is locked (Android foreground service, high-priority notification) (blueprint).
- **WTR-006** (M) The app receives every alert the waiter's pager receives (order ready, new order to approve, manager nudges), and acknowledging in either place acknowledges both.
- **WTR-007** (M) Live item status per table; mark picked up / served.
- **WTR-008** (M) Move table (TBL-005) (blueprint); request the bill, which notifies the cashier. Printing the bill to the POS printer from the app is S.
- **WTR-009** (M) Cancellations and voids follow ORD-011. When needed, a manager enters their PIN on the waiter's device.
- **WTR-010** (M) Out-of-stock items are shown as unavailable in real time (blueprint).
- **WTR-011** (S) Upsell prompts: the top recommendations (REC) for the table's current order.
- **WTR-012** (M) Connectivity: A persistent "Offline" indicator shows when the server can't be reached. Unsent orders are kept as drafts on the device and resent on reconnection with the same idempotency key. They are never silently discarded. The waiter always sees clearly whether each KOT reached the kitchen.
- **WTR-013** (S) Create takeaway orders.
- **WTR-014** (M) Shows the waiter's own pager with battery and connection status, and warns when the pager is offline or low on battery.

## TAB

Section: 6.9 Customer table tablet (TAB)

- **TAB-001** (M) Android app locked in kiosk mode (Android device-owner lock-task mode, managed by MDM). Diners cannot leave the app, change settings or open other apps. Staff exit through a hidden gesture plus a manager PIN.
- **TAB-002** (M) Each tablet is paired to one table (AUTH-009).
- **TAB-003** (M) Session lifecycle. While the table is not open, the tablet shows an idle screen (restaurant branding, promotions ⚙, "Please wait to be seated"). It unlocks when a table session is opened (TBL-003). When the session closes, the cart, order history, feedback and any customer data on the device are wiped.
- **TAB-004** (M) Home screen with four large labelled buttons: Water, Waiter, Bill, Cancel (blueprint), plus the entry to the menu. Water / Waiter / Bill each raise a service request to the table's responsible waiter (pager + app). Bill also notifies the cashier (BILL-015). A raised request stays active, with the button showing "Requested, waiter notified" and the elapsed time, until it is cancelled or resolved. Cancel works like a flight-cabin call button. It cancels the table's active request(s): The waiter presses it on arrival (resolving the request). The diner presses it if the request is no longer needed. If more than one request is active, the tablet asks which to cancel. With one active request, Cancel clears it directly. While active, the request re-alerts the waiter every R seconds ⚙ until acknowledged. If it is not acknowledged within N seconds ⚙ it escalates directly to the manager (NTF- 005). After acknowledgement the tablet shows "Waiter is on the way". The same request type cannot be raised again while one is active (anti-spam).
- **TAB-005** (M) Menu browsing: categories, and item cards with photo, price, veg/non-veg/egg marker, spice level, tags and bestseller badge; item detail with description; filters (veg only, Jain, spicy, bestseller) and sorting; a note on whether prices include or exclude taxes.
- **TAB-006** (M) Search: fuzzy text matching over names, synonyms (MENU-011) and tags. So "something spicy" returns items tagged spicy, and "paneer dishes" returns items whose name, synonyms or tags mention paneer (blueprint, extended).
- **TAB-007** (S) Voice search (blueprint): a microphone button uses Android's on-device speech recognition (English) and feeds the recognised text into TAB-006. It works offline only if the tablet has Android's offline English speech pack installed, which is a site-readiness checklist item (ONB-011). If recognition isn't available, the button explains this and the diner can type instead.
- **TAB-008** (M) Cart: variant/modifier popup (shared component), quantity, special instructions, and a review screen with the subtotal and estimated taxes.
- **TAB-009** (M) Submit → status "Waiting for waiter confirmation" and the waiter is notified (ORD-003, ORD-005). After approval, each item's status is shown live: Received → Preparing → Ready → Served (blueprint note).
- **TAB-010** (M) My order: all items ordered in this session, their status and the running total.
- **TAB-011** (M) Recommendations (REC) on the menu, item and cart screens, each with its reason (e.g., "Goes well with Butter Chicken", "Bestseller").
- **TAB-012** (M) Out-of-stock items become unavailable in real time (blueprint).
- **TAB-013** (M) If the tablet can't reach the server, ordering and service buttons are disabled with the message "Please call a waiter", and the tablet recovers automatically.
- **TAB-014** (S) Feedback after the bill: food and service ratings (1-5) plus an optional comment. The diner can optionally give a phone number, with explicit consent, for a digital bill and feedback follow-up.
- **TAB-015** (M) Device health (battery %, charging, connectivity, app version) is reported to the manager dashboard. A low-battery alert fires at 20 % ⚙.
- **TAB-016** (M) Diner-friendly design: large text, high contrast, plain language, no login, and first order placed unaided within 2 minutes (§7.4).
- **TAB-017** (S) Estimated preparation time per order, from item prep times and current kitchen load.

## QR

Section: 6.10 QR online menu and dine-in ordering (QR)

- **QR-001** (M) Each table has a unique QR code (printable table tent) encoding the restaurant, the table and an unguessable token. Regenerating a table's code invalidates the old one.
- **QR-002** (M) A public, mobile-first website (no app, no login) shows the restaurant's live menu: items, photos, prices, tags, availability, variants, modifiers and combos. It uses the same data model and selection behaviour as every other surface (MENU-012) (blueprint).
- **QR-003** (M) Menu sync (blueprint): menu, price and availability changes are pushed from the local server to the cloud within 30 s when online. While offline, changes are queued in a local outbox and retried automatically with backoff, never silently dropped.
- **QR-004** (M) Browse, search (with synonyms and tags), filter, cart, special instructions and recommendations: best sellers and rules, plus learned pairings from the nightly snapshot.
- **QR-005** (M) Dine-in only. No payment before ordering. Customer name is optional.
- **QR-006** (M) Orders are submitted to the relay through a server-side function, never by writing to the database directly from the browser. The function: validates the table token; validates items against the latest menu snapshot; enforces rate limits (default 5 submissions per 10 minutes per table and per browser ⚙ ); stores the order with its idempotency key.
- **QR-007** (M) Customer-visible status (blueprint): 1. "Sending your order to the restaurant..." 2. "Received, waiting for waiter confirmation" 3. "Your order has been sent to the kitchen" 4. Item-level statuses (S). If the restaurant has not picked up the order within T seconds ⚙ (default 60), the page shows "We couldn't reach the restaurant right now. Please call a waiter." The relay marks the order expired, and the local server rejects expired orders if they arrive later. This way no diner waits for an order that was never received.
- **QR-008** (M) The local server sends a presence signal to the relay every 30 s ⚙. If none arrives for 2 minutes ⚙, the QR site switches to read-only menu mode with a banner and ordering disabled.
- **QR-009** (M) Once received locally, a QR order becomes a normal order (source = QR) that needs waiter approval (ORD-003). The rest of the system treats it like any other order (blueprint).
- **QR-010** (M) If a QR order arrives for a table that isn't open, it still enters pending approval, routed to the responsible waiter of that table's section. Approving it opens the table.
- **QR-011** (S) Call waiter / request bill from the QR page, using the same service-request flow as the tablet, for tables without tablets.
- **QR-012** (M) Performance: the first menu view's Largest Contentful Paint is ≤ 2.5 s on a mid-range Android phone over 4G. Photos are served through a CDN in responsive sizes.
- **QR-013** (M) A privacy notice and terms are linked on the page. No advertising or third- party tracking; only essential, anonymous usage metrics.
- **QR-014** (M) Tenant isolation. No QR code, token or credential of one restaurant can read or write another restaurant's menu or orders. This is verified by automated tests (SEC- 005) (blueprint: dedicated isolation test).

## REC

Section: 6.11 Recommendation engine (REC)

- **REC-001** (M) A three-layer engine runs inside the local server. Results are served to the tablet and waiter app, and published as a snapshot to the QR relay.
- **REC-002** (M) Layer 1, manual rules (highest priority). The restaurant defines rules such as "if the order contains item/category X, suggest item/category Y", each with a priority, an optional time-of-day window, an optional date range and target channels. Rules are managed on the dashboard.
- **REC-003** (M) Layer 2, learned "frequently ordered together" (machine learning). Association-rule mining (e.g., FP-Growth/Apriori, or co-occurrence with lift) over that restaurant's own orders in a rolling window (90 days ⚙ ). Retrained nightly on the local server; no cloud required. Minimum support, confidence and lift thresholds ⚙. Activated only after a minimum order volume (300 orders ⚙ ) to avoid noisy suggestions.
- **REC-004** (M) Layer 3, best sellers. Used when nothing has been ordered yet or no rule applies. Ranked by quantity over the last 30 days ⚙ and segmented by time of day (breakfast / lunch / evening / dinner windows ⚙ ).
- **REC-005** (M) Filters applied to all layers: exclude out-of-stock items; exclude items already in the order, unless the item is marked "repeatable" (e.g., beverages, breads) ⚙; respect the table's veg-only filter; course awareness: favour the next course in a configurable category sequence (starters → mains → breads → desserts → beverages ⚙ ).
- **REC-006** (M) Every recommendation carries a human-readable reason label.
- **REC-007** (M) Recommendations are table-level only: no personal profiles and no cross- visit history in v1.
- **REC-008** (M) Tracking per layer and per item: impressions, taps, add-to-cart, ordered. This feeds the recommendation-performance report (RPT-012).
- **REC-009** (S) The manager can boost or pin items (e.g., high margin, overstocked) and block items from being recommended.
- **REC-010** (C) Personalised recommendations with the diner's consent; A/B testing of strategies.
- **REC-011** (M) Recommendations are returned in ≤ 200 ms on the LAN.

## NTF

Section: 6.12 Notifications, alerts and escalation (NTF)

- **NTF-001** (M) A central notification service in the local server turns events into alerts using rules that decide recipients and channels. Channels: pager, waiter app, POS, manager dashboard, KDS, table tablet display.
- **NTF-002** (M) The manager can configure rules on the dashboard (brief: "notifications as per the configurations made"). For each event type: recipients: responsible waiter, all waiters in the section, all waiters, manager(s) on duty, cashier, or a station; channels; escalation timeout N ⚙ and repeat interval R ⚙. Factory defaults are in Appendix C.
- **NTF-003** (M) Event types (minimum): customer order pending approval; item/ticket ready (blueprint); service request Water / Waiter / Bill (blueprint); ready-not-collected, via the kitchen's "Notify manager" button (blueprint); manager nudge to a waiter (blueprint); order cancelled/modified (to kitchen); device offline or low battery (pager, tablet, KDS, printer); disk space, backup failure, license state change, update available/installed.
- **NTF-004** (M) Acknowledgement. The recipient acknowledges on the pager button or in the app. Acknowledging stops repeats and escalation; the acknowledgement time is recorded for reports.
- **NTF-005** (M) Escalation. If an alert is not acknowledged within N seconds ⚙ (default 60), it goes directly to the manager(s) on duty (on the POS, the manager dashboard, and the manager's pager/app if one is assigned). Escalations are logged and appear in staff reports.
- **NTF-006** (M) Delivery. Alerts are delivered at least once and de-duplicated on the device. Devices resynchronise missed alerts on reconnection. Latency is ≤ 2 s (95th percentile) from event to pager vibration on the LAN.
- **NTF-007** (M) If the responsible waiter's pager and app are both offline, the alert goes to the manager immediately, without waiting N seconds.
- **NTF-008** (M) Manager nudge: choose one or more waiters, then a preset message (e.g., "Come to counter", "Check T7") or short text of ≤ 40 characters so it fits the pager display.
- **NTF-009** (S) A waiter can set "On break". Their alerts then go to the manager until they return.

## PGR

Section: 6.13 Wrist pager (PGR)

- **PGR-001** (M) A wrist-worn device based on the ESP32 family (ESP32-S3 or equivalent), using a pre-certified radio module, with: a vibration motor and an LED; a display showing at least 2 lines × 12 characters, legible indoors (e.g., "T7 READY"); at least one physical button (acknowledge); a rechargeable battery with USB-C or dock charging.
- **PGR-002** (M) Battery life ≥ 14 hours of shift use at a typical load (≤ 60 alerts per hour). This is a prototype gate: it must be demonstrated on real hardware before pager development goes beyond the prototype (§17).
- **PGR-003** (S) Splash resistance (target IP54), a comfortable strap, and operation at 0-45 °C (kitchen environment).
- **PGR-004** (M) The pilot may use off-the-shelf ESP32 watch hardware (for example LilyGO T-Watch S3) if it meets PGR-001 and PGR-002. Custom hardware is future scope.
- **PGR-005** (M) Connects to the staff Wi-Fi (WPA2/WPA3) and to the local MQTT broker over TLS with a per-device credential. The pager subscribes only to its own topic, and broker access rules stop any pager reading another's messages.
- **PGR-006** (M) On an alert the pager: vibrates with a pattern per alert type ⚙ (e.g., ready = one long, service request = two short, manager/escalation = three); lights the LED and shows short text ("T7 READY", "T4 WATER", "T5 NEW ORDER", "MGR: COME TO COUNTER"). Several alerts are queued and a count is shown. A short press acknowledges the current alert; a long press scrolls through queued alerts.
- **PGR-007** (M) Heartbeat every 30 s ⚙ with battery %, signal strength (RSSI) and firmware version. The server marks a pager offline after 3 missed heartbeats. The pager shows a "no connection" icon and vibrates once when it loses the connection.
- **PGR-008** (M) Reliable delivery: MQTT QoS 1 with message IDs for de-duplication. Unacknowledged alerts are delivered again after reconnection.
- **PGR-009** (M) Power management (Wi-Fi power save / light sleep between messages) sufficient to meet PGR-002 without breaking NTF-006 latency.
- **PGR-010** (M) Production devices enable secure boot and flash encryption. Credentials live in encrypted storage. The debug/serial console is disabled or locked. There are no default passwords.
- **PGR-011** (M) Over-the-air firmware updates are signed, use A/B partitions and roll back automatically if the new firmware fails to boot. They are distributed through the local server from firmware released in the Vendor Control Plane.
- **PGR-012** (M) Pairing and assignment: the manager pairs a pager (scan its QR code/serial) and assigns it to a waiter. The server stores which pager belongs to which waiter (blueprint). Re-assignment at shift start takes ≤ 30 s.
- **PGR-013** (M) At low battery (≤ 15 % ⚙ ) the pager alerts both the wearer and the manager.
- **PGR-014** (M) A manager can also wear a pager to receive escalations.

## AUD

Section: 6.16 Audit trail and anti-fraud (AUD)

- **AUD-001** (M) An append-only audit log records every security-relevant and money- relevant action: Access: login, logout, failures, lockouts, overrides. Orders: create, approve, reject, modify, cancel, void. Money: discounts, complimentary items, service-charge removal; bill print, reprint, edit, void; payments; cash in/out; shift close; day-end. Menu: price, menu and stock changes. Administration: staff, role and permission changes; device pairing; settings changes. System: exports, backup, restore, archive, purge; license and update events.
- **AUD-002** (M) Each entry records: server timestamp and business date; actor, approver (for overrides) and device; action, entity, before/after values and reason.
- **AUD-003** (M) Tamper-evident: entries are hash-chained (each includes the hash of the previous one). The current chain-head hash is sent to the Vendor Control Plane with each heartbeat, so later tampering with the local database can be detected. A verification tool is available on the dashboard.
- **AUD-004** (M) Orders, bills, payments and audit records can never be hard-deleted through the application. The database role used by the application has no DELETE permission on these tables. Only the archive-and-purge process (DATA-008) can remove them, and it writes a purge record with checksums.
- **AUD-005** (M) Audit viewer with filters and export.
- **AUD-006** (M) Daily suspicious-activity report ⚙, flagging for example: voids after the bill was printed; bill edits after printing; discounts above threshold; repeated reprints; cash variance above threshold; items cancelled after preparation started; items sent to the kitchen that never appeared on a settled bill; "no-sale" cash-drawer openings.
- **AUD-007** (M) Audit records are retained like financial records (§9.3).

## DATA

Section: 6.17 Storage, backup, archive and purge (DATA)

- **DATA-001** (M) The PostgreSQL data directory and photo store sit on the drive chosen at installation (ONB-002). PostgreSQL listens on localhost only.
- **DATA-002** (M) Automatic local backups: continuous or hourly ⚙ incremental backup (WAL archiving); a nightly full backup to a second location (second disk, external USB drive or NAS ⚙ ). Every backup is integrity-checked. Default retention: 14 daily + 8 weekly ⚙.
- **DATA-003** (M) Encrypted cloud backup: a nightly backup, encrypted (AES-256) on the restaurant PC before upload, stored in India. The encryption key is generated at installation and stored locally (DPAPI). A copy is escrowed in the Vendor Control Plane, wrapped by a vendor KMS key and released only on the Owner's authenticated restore request (audited). The policy is open item OI-10. On by default. The Owner may opt out (recorded in the audit log).
- **DATA-004** (M) Restore: one-click restore from a local or cloud backup onto the same or a new PC (after license re-binding, LIC-004). Targets: RTO ≤ 2 hours once replacement hardware is available. RPO ≤ 1 hour when local backups survive; ≤ 24 hours when only the cloud backup survives. The restore procedure is documented and rehearsed before the pilot.
- **DATA-005** (M) Backup failures alert the manager and are reported to the Vendor Control Plane.
- **DATA-006** (M) Storage monitoring: the dashboard shows disk usage by category (transactions, audit, logs, photos, backups). Warnings at 80 % and 90 % ⚙ of the drive.
- **DATA-007** (M) Operational data is purged automatically after 90 days ⚙: notifications, device heartbeats, debug logs, temporary files, unused photo renditions.
- **DATA-008** (M) Archive-then-purge for business records (brief: "clear some data periodically"). Business records are orders, bills, payments, audit and derived report data. Steps: 1. The Owner (password + 2FA) selects a period (whole financial years ⚙ ). 2. The system writes an encrypted, checksummed archive, plus a human-readable export (invoice register CSV and invoice PDFs), to a chosen location, and adds it to the cloud backup set. 3. It verifies the archive by reading it back. 4. Only then does it delete that period from the live database, and writes a purge record. The purge screen warns clearly if the period is still within the statutory retention period (§12). The restaurant must keep the archive for that period.
- **DATA-009** (S) Archive viewer: open an archive read-only to view or print historical invoices and reports without restoring it into the live database.
- **DATA-010** (M) Full data export in open formats (CSV/JSON plus invoice PDFs) is available to the Owner at any time, including in restricted license mode (LIC-005).
- **DATA-011** (M) Personal-data erasure: on a diner's request, their phone number/name is erased or anonymised in non-invoice records. Invoices are kept as tax law requires.
- **DATA-012** (M) Sizing target: 5 years of transactions for a restaurant at design capacity (§7.2), excluding photos and backups, fit in ≤ 100 GB. The development team validates this with a data-volume test.

## LIC

Section: 6.18 Licensing and subscription enforcement (LIC)

- **LIC-001** (M) Each installation holds a license file signed by the vendor (Ed25519 or equivalent) containing: restaurant ID, installation ID and PC fingerprint; plan, entitled modules (all modules in v1), device limits (tablets, pagers, waiter devices, KDS screens); issue date, valid-until date, grace days and state.
- **LIC-002** (M) Rolling validity: a license is valid for 30 days ⚙ from issue and renewed automatically (at least daily) while online. The restaurant works fully offline until valid- until (blueprint: cached license).
- **LIC-003** (M) The local server verifies the license at start-up and periodically, and client apps get their entitlements from the server. The vendor's public key is embedded in the software; a missing, unsigned or tampered file puts the installation into Restricted state.
- **LIC-004** (M) Machine binding: the license is bound to a PC fingerprint that tolerates minor hardware changes (e.g., 3 of 5 identifiers must match). Moving to a new PC is a support action in the Vendor Control Plane (audited).
- **LIC-005** (M) License states (brief: "remotely stop its functioning if payment is not made"): State Entered when Restaurant experience Active Subscription paid Full functionality Payment due Invoice overdue (recorded in Control Plane) Daily polite reminder on POS and dashboard; no restriction Grace Vendor moves to grace, or overdue beyond N days ⚙ Banner on all staff screens with days remaining (7 days ⚙ ) Restricted Grace ends, license expires while offline, license invalid/tampered, or vendor suspension No new table sessions, orders or KOTs. Can still: finish and bill already open tables, print, view reports, export all data. Backups continue. Terminated Contract ended As Restricted; data export stays available; nothing deleted Rules that always apply: A move into Restricted takes effect only at the start of the next business day, never in the middle of service. The platform never deletes, encrypts or withholds the restaurant's data. All state changes are logged in the Control Plane and locally.
- **LIC-006** (M) Reactivation takes effect within 1 minute of payment being recorded in the Control Plane (when online). For offline sites, a signed reactivation code can be entered by the Owner (e.g., received by phone).
- **LIC-007** (M) Anti-tamper measures: clock-rollback detection (last-seen time stored and signed, compared with the server time in heartbeats); signed binaries, integrity checks and obfuscation of the license module (SEC-011). Tamper events are reported to the Control Plane.
- **LIC-008** (M) The license state and remaining days are always visible to the Owner. Reminder wording is polite and precise.
- **LIC-009** (M) Timelines and behaviours in LIC-005 must match the subscription agreement (Business Owner, §19).
- **LIC-010** (C) Selling modules separately, using the entitlement fields already in the license.

- **NFR-M01** (M) Object-oriented design and SOLID principles (brief: "OOPS principles"): clear domain models and services in the backend; dependency injection (NestJS modules); reusable components so the same code is used everywhere it applies (PIN pad, menu item card, modifier popup, order status chip, etc.).
- **NFR-M02** (M) Pricing, tax, discount, order state machines and recommendation logic live in a framework-free domain package with unit tests. They are shared by the server and, where useful, the clients.
- **NFR-M03** (M) TypeScript strict mode everywhere (blueprint). Linting and formatting are enforced in CI. any is not allowed without a documented reason.
- **NFR-M04** (M) Test coverage: ≥ 85 % of lines in the domain package and ≥ 70 % overall for the backend. End-to-end tests cover every critical scenario in §18.
- **NFR-M05** (M) Every change goes through a pull request with at least one reviewer, and two for security-sensitive code (auth, licensing, billing, crypto, sync).
- **NFR-M06** (M) Documentation: ADRs for significant decisions; generated API/event docs (INT-002); runbooks for installation, restore, update, rollback and incident response; an onboarding guide for new developers.
- **NFR-M07** (M) Dependency hygiene: lockfiles, automated update PRs, and a license check that blocks licenses incompatible with commercial distribution.
Section: 7.8 Observability

- **NFR-O01** (M) Structured (JSON) logs with correlation IDs across devices, server and cloud. Local log rotation by size and age.
- **NFR-O02** (M) Crash and error reporting from every component to a vendor error- monitoring service, with personal data and secrets scrubbed before sending.
- **NFR-O03** (M) Health metrics are sent in heartbeats (VCP-005).
- **NFR-O04** (M) The server PC's clock is synchronised by NTP. Devices take their time from the server, and all business timestamps use server time.
Section: 7.9 Installability and supportability

- **NFR-I01** (M) Installing on a PC that meets the spec takes ≤ 30 minutes, excluding menu set-up.
- **NFR-I02** (M) The installer can repair an installation. Uninstalling keeps the data unless the Owner explicitly chooses to delete it (password + 2FA).
- **NFR-I03** (M) A single "Support" screen shows versions, service status, disk, backup and license state, and connected devices.

## SEC

Section: 8.1 Standards and baseline

- **SEC-000** (M) A threat model (STRIDE) is produced for each component during design and updated at each major release. It covers the LAN, the pager channel, the relay, the update pipeline and the license mechanism.
Section: 8.2 Requirements

- **SEC-001** (M) Encryption in transit everywhere. Cloud: TLS 1.2+ (1.3 preferred) with HSTS. LAN: HTTPS/WSS for apps and browsers, MQTTS for pagers. How LAN certificates are issued is decided in an ADR (open item OI-07). Options: (a) a per-installation private certificate authority, trusted and pinned in the vendor's own apps and installed on paired manager browsers; or (b) publicly trusted certificates for a per-restaurant hostname resolving to the LAN IP, issued via DNS validation by the Control Plane.
- **SEC-002** (M) Secrets are never in source code or in app bundles. API keys for cloud services live only in vendor cloud secret stores and CI. Restaurant installations get per- tenant, scoped credentials from the Control Plane. Clients get short-lived tokens.
- **SEC-003** (M) Authorisation: deny by default, checked on the server, including object- level checks (a tablet may act only on its own table, a waiter only on permitted tables, a pager only on its own topic).
- **SEC-004** (M) Input handling: validation at every boundary with shared Zod schemas; output encoding; parameterised queries only (Prisma), with no string-built SQL; uploads checked by content type and size, images re-encoded and EXIF stripped.
- **SEC-005** (M) Cloud tenant isolation (blueprint: per-restaurant filtering as a dedicated test): Row-Level Security on every relay/Control Plane table, deny by default. Local servers use per-tenant credentials, never a service-role key. Browsers never write tables directly (QR-006). Automated cross-tenant access tests run in CI. Each local database holds only one restaurant, but still stores the restaurant ID on every record for consistency with the cloud.
- **SEC-006** (M) Key management: The license-signing private key is in a cloud KMS/HSM and is never on a developer machine. Code-signing keys are on hardware tokens or cloud HSM. Local secrets (pepper, backup key, TLS keys) are protected by Windows DPAPI. Device credentials are in Android Keystore or ESP32 encrypted storage.
- **SEC-007** (M) Data at rest: PostgreSQL bound to localhost, with a dedicated service account and least-privilege database roles (AUD-004). BitLocker recommended on the server PC (site-readiness checklist). Backups and archives encrypted with AES-256. Diner phone numbers encrypted at application level (S).
- **SEC-008** (M) Network: Staff devices on a network separate from guest Wi-Fi (§11). The server firewall allows only the required ports, from the staff subnet only. No inbound connections from the internet; outbound traffic only to an allow-list of vendor/relay domains.
- **SEC-009** (M) Abuse protection: rate limiting on login, pairing, QR submission and service requests; lockouts (AUTH-003).
- **SEC-010** (M) Mobile: no secrets or personal data in logs; pinned certificates for server connections; kiosk lock (TAB-001); MDM policies: USB debugging off, app installation blocked, remote lock/wipe. Root/tamper detection on waiter devices and screenshot blocking on PIN screens are S.
- **SEC-011** (M) Desktop (Electron): contextIsolation on, nodeIntegration off, sandboxed renderers; strict Content-Security-Policy; no remote content in privileged windows; IPC allow-list; Electron fuses configured (RunAsNode disabled, ASAR integrity where supported); Electron kept on a supported version.
- **SEC-012** (M) Pager: PGR-005, PGR-010 and PGR-011; unique per-device credentials; broker access rules.
- **SEC-013** (M) Software supply chain: lockfiles; dependency vulnerability scanning; static analysis (SAST); secret scanning in CI; an SBOM for every release; protected branches; mandatory 2FA on the code host; least-privilege CI secrets; builds and signing only in CI, never on developer laptops.
- **SEC-014** (M) Signed updates (UPD-007).
- **SEC-015** (M) Security logging: Security events are audited (AUTH-013, AUD-001). No PINs, tokens or unnecessary personal data in logs. Cloud security logs are kept for at least 180 days, in India (§12). The Control Plane alerts on anomalies (repeated tamper events, mass failed logins, cross-tenant access attempts).
- **SEC-016** (M) Incident response plan before the pilot: severity levels, contacts and on-call; regulatory reporting (CERT-In within 6 hours for reportable incidents; data-breach notifications under DPDP, §12); templates for communicating with restaurants; an annual tabletop exercise.
- **SEC-017** (M) Security testing: automated authorisation tests; DAST on the QR site, relay and Control Plane; an independent penetration test covering web, API, Android, desktop, LAN and pager, before the first paid rollout and then annually or at each major release; zero open Critical/High findings at go-live; Medium findings have a dated remediation plan.
- **SEC-018** (M) Vendor access: MFA on all vendor systems, least privilege, quarterly access reviews, and all production access audited.
- **SEC-019** (M) Privacy by design: collect the minimum personal data, record consent with its purpose and timestamp, and support erasure (DATA-011).
